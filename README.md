# zhbot
Telegram 综合报单机器人 V1.0

这是从需求独立开发的**新实现**。指定 WIP 快照未能通过受支持的 Library 传输取得，因此没有验证或沿用其源码与旧测试。当前为开发审查版本，未部署、未连接真实 Telegram、未接通真实 OKPay。

## 离线验证

需要 Linux 和 Python 3.12+；运行和测试只使用标准库，无需安装依赖。在仓库根目录执行：

```bash
python3 -m unittest discover -v
python3 -m zhbot demo
python3 -m compileall -q zhbot tests
```

演示仅使用临时 SQLite、虚构身份、虚构文件 ID 和模拟支付。它完成“模拟充值 5 → 报单冻结 3 → 多部分回执全部发送 → 扣除 3”，输出可用 2、冻结 0、订单 completed、3 条账变和 5 项回执，不发送网络请求。

## 已实现范围

- 用户注册、可用项目、文字/多图/多文件草稿、完整预览和显式确认；确认前不冻结。
- 管理员私聊管理项目、查看订单、持久化编辑和预览混合回执、交付或终止订单。
- SQLite 原子账本、重复操作去重、余额约束与并发确认保护。
- 持久化发送队列，逐项记录 API 发送确认；完整交付后扣冻结积分。明确首项拒绝可失败释放；部分交付或结果不明先保留冻结、人工核实。
- 长轮询更新去重与原子游标、坏更新隔离、重启恢复、同机机器人锁和数据库锁。
- 统一有界 ASCII 数字输入，拒绝 Unicode 数字和过长数字，防止 int 转换异常堵塞轮询。
- 离线充值边界：整数 USDT、最低 1、600 秒期限、证据核对、交易号唯一与原子入账。

## 配置与启动入口

仅在用户另行批准联网验证或部署后使用。此次开发没有执行此启动命令，没有提供任何真实令牌：

```bash
python3 -m zhbot run --db var/bot.sqlite3
```

启动从环境读取 `TELEGRAM_BOT_TOKEN` 和逗号分隔的 `TELEGRAM_ADMIN_IDS`。不要把令牌写入源码、命令历史、PR、日志或聊天。管理员与客户都先私聊 `/start`。程序核对机器人身份和 webhook；已有 webhook 时退出，不会自动删除。每个机器人必须使用专用数据库及单个运行实例。

**真实充值始终关闭**：运行入口固定使用 DisabledGateway，没有环境开关、商户凭据读取或真实 OKPay HTTP 实现。`/recharge` 会明确拒绝。模拟适配器只供离线演示/测试使用，不能作为真实支付验证依据。

## 命令

| 用户 | 操作 |
| --- | --- |
| `/start`、`/help`、`/balance`、`/projects` | 注册、帮助、余额、项目 |
| `/new 项目ID` | 创建单笔客户草稿，随后发送文本、图片、文件 |
| `/text 内容` | 提交以 `/` 开头的文字 |
| `/draft` | 按顺序完整预览草稿，并给出确认命令 |
| `/confirm 草稿ID 版本` | 只接受已完整预览的当前版本；原子冻结 |
| `/undo`、`/clear`、`/cancel` | 撤销末项、清空当前编辑内容、取消客户草稿 |
| `/orders [页码]`、`/order 订单ID` | 查看自己的订单和材料 |
| `/payments`、`/check 充值单号` | 查看自己的充值记录/登记查单；真实查单未开放 |

| 管理员（仅私聊） | 操作 |
| --- | --- |
| `/admin`、`/adminprojects` | 管理帮助、全部项目 |
| `/project new 价格 on 名称` | 创建项目 |
| `/project 项目ID 价格 on或off 名称` | 修改项目或上下架 |
| `/orders [页码]`、`/order 订单ID` | 查看全部订单和材料 |
| `/receipt 订单ID` | 选择回执；之后发送的文本、图片、文件进入该回执 |
| `/preview 订单ID` | 完整预览当前回执；编辑会使预览失效 |
| `/deliver 订单ID 版本` | 当前管理员完整预览后确认交付 |
| `/fail 订单ID 原因` | 终止尚未开始交付的订单并释放冻结 |
| `/review [页码]` | 查看不确定交付和异常充值 |
| `/resolve 消息记录ID sent 核实依据` | 人工确认该项已经送达；不重发该项，继续剩余部分 |
| `/resolve 消息记录ID failed 核实依据` | 人工确认整单交付失败，取消剩余发送，释放全部冻结 |

管理员使用 `/draft` 可切回自己已有的客户草稿；空草稿会先切换目标并提示添加材料，不会继续写入之前的客户回执。没有客户草稿时也会退出回执编辑，并提示 `/new` 创建；`/receipt` 可显式切回回执编辑上下文。每个客户同时一个草稿，每份材料/回执最多 20 项，文字最多 3500 UTF-16 单位、附件说明最多 1000；单次积分范围 1～1,000,000。

## 交付与恢复

`submitted → delivering → completed`：所有回执部分收到 API 成功响应后才扣费。API 接受消息不等同用户已读。回执逐条发送，不组合成 Telegram 相册，以保留文字、图片、文件的混合顺序。

超时、5xx、异常响应或进程在发送后记录前退出：`delivery_review`，保留冻结，不自动重发。管理员必须先核对聊天记录与发送队列，再使用 `/resolve` 并填写依据。核实失败时整单不扣费，即使有部分内容已送达。

重启沿用同一数据库，自动把 sending 转为 unknown；尚未发送的队列保留。预览/普通通知结果不明时也不自动重发；用户可重新执行查询或预览。数据库写入失败会停止运行，不能推进 polling 游标。内部处理错误会回滚该条业务变更并隔离更新，留下无原始内容的审计记录。

运行数据包含客户文本和 Telegram 文件 ID，应限制目录权限。附件字节仍由 Telegram 保存，本程序不下载它们，也未验证 Telegram 的长期保留保证。停机后备份整个数据库；运行中应使用 SQLite 在线备份 API，不能只复制主文件而丢掉 WAL。不要在备份恢复后盲目重发旧队列，须先核对实际聊天记录。没有分布式锁，不支持多主机并行运行；没有兼容缺失快照数据库的迁移工具。

## 支付与证据限制

1 USDT = 1 整数积分、最低 1、本地 10 分钟有效期。此期限不意味着 OKPay 链接会自动失效。超过期限首次观察到已支付、缺少可信付款时间、身份或金额不符、未知创建结果，一律待人工核实。

目前仅实现内部模拟证据契约，未实现或验证真实接口、签名 SDK、回调、付款人字段或支付时间能力；没有人工强制给真实充值加分的命令。必须取得原始官方文档及 SDK，完成独立审查并获得用户批准后再设计和验证真实接入。
