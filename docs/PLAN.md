# V1.0 重建计划与设计

依据：2026-11-06 用户指令和 Notion 40fafec1362381239ce0cf53ec1b7ebc（已完整读取）。从 main dc6b4336 新建 codex/telegram-v1-rebuild；不读取或恢复旧 PR 源码。

采用 Python 3.12 标准库、SQLite WAL、Telegram HTTP 长轮询。相比 ORM/异步框架方案，单管理员/单进程下依赖少，资金事务与故障边界更易检查。未来并发扩展可替换持久层。

阶段一：迁移、商品、持久草稿、订单批次、钱包与审计。BEGIN IMMEDIATE 保护余额；每笔事件唯一键，整数积分；商品快照。余额不足提交使草稿失效且无订单/冻结。
阶段二：Telegram 私聊客户/管理员交互；逐项商品向导；引用回复回单；持久通知队列；交付前落盘 sending，Telegram 明确成功后记录 message_id，全部成功才扣费；超时/崩溃进入 uncertain，禁止自动重发/退款。人工核实命令记录证据。
阶段三：OKPay 真实 SDK 适配及安全归属入账。必须先确认官方契约，不编造协议；若文档/SDK/凭据缺失，此阶段标为阻塞，生产收款关闭，不能宣称 V1 全部完成。
阶段四：离线事务/并发/幂等/故障/权限/交互测试，部署和恢复文档，阶段提交与新草稿 PR。不得合并 main 或部署。

自定义字段采用逐项输入，各字段配置 text/photo/document；纯文字单字段支持一行一单，多字段按一组收集成单笔。媒体可增删，不允许媒体批量。未确定的自动提醒和过期策略不添加。

测试重点：整批拒绝与并发超支；重复确认/调整/入账；跨客户回调伪造；回单暂存不可提前泄露；交付不确定不扣/不退；批次终态唯一汇总。SQLite 备份 API，迁移版本管理；敏感值不写仓库/日志。
