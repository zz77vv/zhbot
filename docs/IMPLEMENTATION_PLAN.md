# V1 新实现计划

本轮获授权在指定快照无法取得时独立开发。这是新实现，不是经过验证的快照续作。技术选择沿用已给需求：Python 3.12 标准库、SQLite、Telegram long polling；不引入服务或真实支付。

## 结构与状态约束

- `zhbot/core.py`：统一有界 ASCII 整数验证、业务异常。
- `zhbot/store.py`：SQLite schema、嵌套事务、查询。状态变更由服务统一完成，使用 BEGIN IMMEDIATE 和唯一账变键。
- `zhbot/service.py`：用户/项目/订单/回执/发送队列/恢复。所有外发先持久化；发送前标记 sending；未明确确认的结果进入人工核实，禁止自动重发。完整发送才扣冻结积分。
- `zhbot/payments.py`：默认禁用的支付入口及仅供离线测试的模拟适配器；没有真实 OKPay 网络实现。支付时间、身份、交易号等证据不完整时不入账。
- `zhbot/app.py`：中文命令路由；纯文本与附件按当前持久化上下文添加；单条更新在数据库事务内记录处理结果、回复队列和 polling 进度。
- `zhbot/telegram.py`、`zhbot/__main__.py`：标准库 HTTP 适配、单进程文件锁、循环与恢复；令牌只从环境读取，日志不输出请求 URL 或原始异常。
- `tests/`：unittest，临时数据库、模拟传输，全部离线。

收据与客户草稿使用 revision；完整预览成功后才能确认该版本。多部分消息逐条发送，以保留文本、图、文件混排顺序。没有确认送达的预览不能解锁交付。管理员人工核实必须附审计原因。

## 分阶段执行

1. 写账本与订单失败测试，再实现注册、项目、草稿、确认冻结、失败释放；覆盖余额不足、重复与并发。
2. 写持久化回执/队列故障测试，再实现预览版本门槛、完整发送扣款、部分/不确定结果、重启与人工核实。
3. 写充值测试，再实现整数金额、600 秒期限、本人/币种/金额/状态/时间验证、平台交易号唯一；默认禁用真实支付。
4. 写路由和 polling 测试，再实现私聊管理员命令、所有权校验、持久化交互状态、更新去重、Unicode/超长输入与坏更新隔离。
5. 写 HTTP/运行入口测试，完成单实例锁、文档、离线端到端演示；运行全套测试与静态编译。独立审阅后修复重要问题，更新草稿 PR，禁止合并/部署。

## 审查焦点

- 所有数值入口拒绝 Unicode 数字、布尔和超长输入，后续更新继续处理。
- 网络结果不确定及发送后记账前崩溃：不重复发、不误扣、不误释放。
- 预览后草稿变更、重复点击和多个管理员并发不得交付错误版本。
- 多连接余额竞争、事务中断、同一交易跨单使用不得破坏账本。
- 截止后查到成功、缺少可信支付时间或付款人时只进入人工核实。
