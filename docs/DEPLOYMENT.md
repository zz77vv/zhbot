# 部署与异常恢复

本文供部署和隔离测试使用。当前已有独立测试实例，并核对过一笔 2 USDT 实付入账。正式上线前还需完成各业务流程和异常恢复验收。

## 环境

Linux/Python 3.12+；非 root 专用账号；持久磁盘（不要将 SQLite 放在网络共享盘）；允许 HTTPS 访问 `api.telegram.org`。OKPay收款放通 `api.okaypay.me`。校准系统时间。一个数据库只运行一个机器人进程；`flock` 防止本项目多实例共享数据，Telegram Token 也只由一个轮询实例使用。不能同时启用 webhook/getUpdates。

从仓库根目录使用 `python -m zhbot run`，保持 `zhbot/` 与 `migrations/` 一起部署。启动迁移是版本化向前迁移，迁移前停服务并备份；不支持自动降级。没有第三方依赖安装步骤。

环境变量见 `.env.example`，真实文件限制600，仅专用用户可读。SQLite、WAL、SHM和备份目录也需限制权限。程序在创建数据库前设置 umask077；日志不打印Token、商户密钥或完整客户资料。主机日志和备份仍按敏感信息管理。

可使用 systemd：WorkingDirectory 指向仓库，ExecStart 指向 Python 3.12 的绝对路径并加 `-m zhbot run`，EnvironmentFile 指向受保护文件，User 指向专用用户，Restart=on-failure、UMask=0077。不要在 unit 文本里硬编码真实密钥。配置文件不包含可执行部署脚本，本次不启动服务。

## 日常操作

- `/start` 客户流程；`/admin` 私聊管理；`/balance` 当前可用/冻结。
- `/adjust 客户ID 增减整数积分 原因`，按钮二次确认，流水来源为「管理员调整／其他收款」。不能扣减冻结积分或导致负余额。
- 后台「异常列表」列出不确定订单、回单、通知、中断入站更新。
- 钱包 `wallets`，流水 `ledger`（含余额快照、唯一事件键、时间），操作日志 `audit`；SQLite只读查询可审计，禁止直接 UPDATE 钱包或流水。

## 交付恢复

Telegram 不能提供本项目需要的发送幂等键。HTTP超时可能已经送达，所以在网络发送前先将回单写为 sending，拿到message_id才写为sent；send状态中崩溃或超时则订单进入 uncertain，保留冻结，不自动重发、不自动退款。

1. 管理员核实对应客户聊天记录及已保存message_id，逐条查明 sending 回单是否实际送达。
2. 已送达：`/resolve 回单ID sent Telegram消息ID 核实证据`。
3. 已确认没有送达：`/resolve 回单ID retry 0 核实证据`。只有这个结论才允许后续发送，盲目重试会造成重复回单。
4. 全部待核实回单处理后，队列恢复，仅发送 staged 回单，跳过sent。全部sent才结算。
5. 如果结算/存储异常导致订单uncertain但没有sending回单：`/resume 订单ID 核实证据`。不确定回单尚未逐条核实则拒绝恢复。该操作不会直接把订单当成功或退款。

恢复操作都校验唯一管理员并留审计。不可为绕过冻结而手动加分后又重放退款。

## 通知与入站更新

`events` 持久化新订单通知、退分通知、最终批次汇总。唯一键防业务重复创建；通知发送超时/中断进入 uncertain。核实后使用 `/event 事件ID sent 消息ID` 或 `/event 事件ID retry 0`；retry 仅限已确认未送达，否则可能重复通知。

入站update_id先记processing，处理完成写done，重复ID跳过。处理期间崩溃可能已产生部分业务副作用，重启标uncertain，不盲目自动重放。这保证资金操作可查，但不保证入站交互永不丢失。管理员需查草稿/订单/流水，核实后让客户重新操作。草稿确认、退款、扣费、手动调整及充值拥有独立幂等保护；未完成的商品向导/普通回复可能需要重新输入。异常清单保留供审计；不要直接删除inbox重放。

## 备份与恢复

使用SQLite在线备份API，避免只复制db遗漏WAL：

```sh
# 命令行会请求数据库锁，因此先停止轮询进程。
python -m zhbot backup --destination /secure/backups/zhbot-YYYYMMDD.sqlite3
python -m zhbot check
```

定时频率和保留期限由运营者决定；备份加密并限制权限，定期隔离恢复演练。恢复时停止机器人，保存当前db/WAL/SHM和日志，整体切换到确认一致的备份，再执行integrity_check和账本核对。不要将旧WAL文件与新db混用。

`check` 和 `backup` 要求源库已经存在，并以只读方式打开。新安装先运行 `migrate`，升级前先备份旧库再迁移。`check` 完整性检查失败时以非零状态退出。备份拒绝已存在的目标文件、软链接和硬链接，通过临时快照验证完整性后才发布为指定文件。

批量回单发送异常时从「异常处理」取得事件编号，核实后使用 `/event 事件ID sent 消息ID` 结算，或 `/event 事件ID retry 0` 重试。确认整条回单未送达且需要取消时，可用 `/event 事件ID cancel 0` 退回整批冻结积分。

**回滚备份可能抹掉备份后的实付/交付证据。恢复后不能直接自动发货/入账。** 先保持机器人停止，将备份后的Telegram消息、商户交易和流水逐笔核对，再决定人工修复；不能假定备份状态等于外部世界。支付可由客户主动可信查单恢复，未实现自动批量商户对账。

## 正式启用前

先按 docs/OKPAY.md 配置隔离测试并完成真实联调，再验证商品/所有资料类型/批量不足/双击/退款/重启/阻断客户/网络故障/备份恢复，验证消息及冻结账实一致。当前无确定未处理提醒阈值或自动过期退款，也无主动客户取消接口。不要自行开启生产服务、收费或合并main。

## OKPay 操作补充

默认 `OKPAY_ENABLED=false`，测试环境显式启用后提供真实付款链接。充值菜单直接输入金额，单笔卡片可主动查单。创建超时保留原单，再次输入相同金额打开原单。可信查单待付但链接丢失时，管理员按 docs/OKPAY.md 的 `/paymentlink` 指令核实恢复。商户确认原单不存在或已永久失效时，可以用 `/paymentclose` 留审计关闭。当前通过主动查单入账。
