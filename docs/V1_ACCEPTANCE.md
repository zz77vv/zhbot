# Telegram 综合报单机器人 V1.0 验收边界

本文件记录本次接管的需求与待验收条件，不表示机器人已经实现或通过测试。

## 范围

Python、SQLite、Telegram long polling。只支持人工单笔报单和人工回执交付；不接上游，不做批量单，不部署，不启用真实支付，不提交凭据。指定 WIP 快照传输失败后，本轮获明确授权从需求独立新实现；不声称延续或验证了缺失快照。

## 必须验证的业务流程

| 流程 | 验收条件 |
| --- | --- |
| 注册与权限 | 用户显式注册；管理员权限由受信配置中的 Telegram ID 判定；管理操作仅限管理员私聊；用户只能操作自己的订单与充值 |
| 项目 | 管理员私聊创建、修改、上下架；用户只可选择可用项目；价格为正整数积分；确认时重新核对项目可用性与价格，价格变化需用户重新确认 |
| 报单 | 文本、多张图片和多个文件按顺序持久化；展示完整草稿并显式确认后才冻结积分；重复确认只创建一次订单、冻结一次 |
| 余额账本 | 可用余额与冻结余额不得为负；冻结、扣除、释放、充值与对应状态变更必须在同一 SQLite 事务内；账变唯一键防止重复记账 |
| 回执 | 管理员可持久化编辑混合文本、多图和多文件回执，预览后确认交付；记录每一部分的发送状态和 Telegram message ID |
| 成功 | 只有全部回执部分被明确确认发送成功后，才能原子扣除冻结积分并结束订单；重复完成不得重复扣除 |
| 失败 | 确认失败终止时释放冻结积分；重复失败不得重复释放；已完成订单不得再次释放 |
| 不确定发送 | 超时、断线或进程在发送后记录前崩溃，都可能已经送达；保持积分冻结并进入人工核实；不自动重发、不自动扣款、不冒充发送失败 |
| 恢复 | 订单草稿、回执草稿、账变、发送尝试和 polling 进度持久化；重启识别未完成发送并转人工核实；禁止两个进程并行消费同一 polling 流 |
| 输入异常 | 非 ASCII 数字、负数、小数、布尔值、超长数字、非法回调和过期操作均安全拒绝；单条坏输入不得停止后续更新处理 |

Telegram 发送成功只能证明 API 接受该消息，不能证明用户已经阅读；机器人不得把回执已读当作已有能力。部分交付或结果不确定时保持冻结，必须先核实再做最终状态决策。

## 充值规则

仅 USDT，1 USDT = 1 个整数积分，最低 1，拒绝小数，支付单有效期 10 分钟，用户主动查单。创建前持久化本地单号；创建结果不明时保留原单号并进入核实，不能换号重复创建。

只有受信来源验证通过，且商户、本地单号、平台交易号、付款人 Telegram ID、金额、币种和已支付状态全部匹配时，才可能入账。以平台交易号建立跨支付单唯一约束，支付状态、积分和账变原子提交。

超时到账、付款时间缺失或无法核实、付款人缺失或不符、金额或币种不符、交易归属冲突、请求结果不明均进入人工核实，不自动入账。10 分钟是本地业务截止时间，不代表平台支付链接会自动失效。

## 测试阶段

1. 在空应用基线上开发并记录新测试结果。旧版“31 项测试通过”不作为本实现证据；以后取得快照时须单独审查差异。
2. 用假 Telegram、假支付适配器、临时 SQLite 数据库验证注册、私聊权限、项目、草稿与确认流程。
3. 验证重复更新、重复回调、并发确认、余额竞争、事务回滚、重复充值与跨订单交易号冲突。
4. 对混合多部分回执注入每一部分发送前、发送中、发送后和记录前故障，验证恢复状态与积分不变式。
5. 在 polling 入口验证 Unicode、超长数字及随后合法更新，证明坏输入不会堵塞队列。
6. 审查真实支付开关默认关闭且无法绕过。确认官方资料与用户批准前，不连接真实支付、不修改服务器、不部署。
