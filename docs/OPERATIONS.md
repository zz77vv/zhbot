# 运行、恢复与备份说明

当前仅为开发审查版。本轮只提交模板，未登录服务器、安装服务、设置令牌、发起真实 Telegram/OKPay 请求或部署。以下操作由操作者在另行批准后执行；真实充值仍固定关闭，没有支付凭据或开关。

## 配置与启动前检查

需要 Linux、Python 3.12+、单主机单实例、专用数据库与机器人；同一机器人禁止使用不同系统用户或不同临时目录启动多个进程。先在隔离副本执行 `python3 -m unittest discover -q` 和 `python3 -m zhbot demo`；demo 使用临时数据库，不会为真实客户发放积分。

`config/zhbot.env.example` 只含两个占位项：`TELEGRAM_BOT_TOKEN` 和逗号分隔的 `TELEGRAM_ADMIN_IDS`。管理员 ID 应来自本人私聊机器人的菜单/余额页；不要按用户名猜人，不把令牌写进命令历史、聊天、工单或仓库。客户先私聊 `/start`；已配置管理员可直接私聊 `/admin` 注册并打开管理菜单。新用户余额为 0；管理员在“管理后台 → 积分管理”选择已注册用户、增加/扣减数额、填写原因、核对确认页后提交，不能用演示数据代替真实运营记账。

systemd 示例位于 `config/zhbot.service.example`，假设只读代码在 `/opt/zhbot`、数据库在 `/var/lib/zhbot`、配置在 `/etc/zhbot/zhbot.env`，专用非登录用户/组 `zhbot` 已存在。复制前核实 Python 路径、目录权限和配置文件属主；配置文件可由 root 持有、zhbot 组只读，权限不宽于 0640。代码不要放在服务用户不可访问的个人主目录。服务使用受限写目录，并保留标准临时目录以共享同运行用户的机器人锁；不需要 Docker、反向代理、数据库服务或开放入站端口。

启动入口为 `python3 -m zhbot run --db /var/lib/zhbot/bot.sqlite3`。程序先核对 getMe、webhook 和本机排他锁；已有 webhook 会退出，不会删除。数据库绑定机器人 ID，不能换机器人复用。示例服务文件安装到 systemd、daemon-reload、enable/start 等均属于部署，本次没有执行。

## 日常操作

客户：“开始报单 → 选择项目 → 发送文字/多图/文件 → 完整预览 → 确认报单并冻结积分”；“我的订单”查看状态和原始材料，“积分余额”查看最近账变。菜单不会成为材料；返回首页会退出编辑目标但不删除草稿/回执。使用“我的草稿”或订单内“编辑回执”恢复编辑。每单最多 20 项，逐项发送，不合成相册；以 `/` 开头的材料用 `/text 内容`。`/menu` 退出输入步骤；命令兼容入口仍保留在 README。

管理员：“订单管理 → 订单 → 编辑回执 → 发送文字/图片/文件 → 完整预览 → 确认交付”。最后一项发送得到确认后才扣冻结积分。项目新增/改价/上下架后，旧项目版本的客户草稿须取消并重建；不会静默按新价冻结。人工扣分只用可用积分，不碰冻结；单次最多 1,000,000，原因最多 500 UTF-16 单位。增加积分还会为现有冻结积分全部退回预留余额上限空间。确认期间余额变化会拒绝旧确认，须重新核对。

按钮绑定本人、机器人、私聊、已确认发送消息、菜单代次与业务版本，30 分钟后过期。旧按钮/重复确认不会重复记账；发送 `/menu` 获取新菜单。需要定位操作时保存本地审计记录，不导出原始 token。UI 状态及去重记录持久化，重启可恢复未完成输入；没有自动清理审计/UI 历史的功能，应监控磁盘空间。

## 交付异常与人工核实

“订单管理 → 订单 → 逐条交付检查”显示每一项的顺序、消息记录 ID、类型、实际收件人、状态和 Telegram 消息编号（未确认则明确显示未确认），以及有界的原因摘要。摘要截断时，以本地 messages/audit 完整依据为准。`sent` 仅表示 API 接受或有人明确核实，不表示客户已读。

超时、5xx、程序在发送后落库前退出时，发送结果未知：保留冻结、不自动重发。先核对真实聊天记录和实际收件人，使用“核实第 N 项”：选择“已核实该项送达”或“已核实整单交付失败”，填写具体依据，再核对二次确认页。确认送达不重发该项，允许队列继续剩余部分；确认整单失败会停止剩余部分并释放全部冻结，即使此前有部分送达。无法判定时不要确认任一结果，保持待核实。

“待核实事项”也列出异常充值和身份隔离单。本地关闭不加分、退款或取消上游，不清除身份隔离。人工积分调整是单独有审计的业务行为，不代表某笔充值被认证，不修改 payments。不得以回调/查单到达时间猜实际付款时间。

## 停机与撤权

正常发送 SIGTERM/systemd stop 后等待进程退出，最迟可能等待当前长轮询/网络调用。不可同时运行另一实例。`Restart=on-failure` 只是服务进程重启；数据库恢复仍将 sending 标成 unknown，不会重做不确定交付。权限变更应停旧实例、改管理员 ID 配置并重启；撤权不撤回已经发出或已在网络中的内容。撤权后未发送管理内容取消，旧管理按钮和未完成输入拒绝，已确认客户交付继续，不自动释放冻结。

## 备份与恢复

数据库包含客户文本、Telegram file_id、用户 ID 和审计原因，应限制备份访问，使用受控存储并规定保留期限；不要把库提交 GitHub。附件字节仍由 Telegram 保存，本程序不下载，未验证永久保留保证。

最简单的备份是在停止服务、确认进程退出后复制整个数据目录（含 SQLite 的 WAL/SHM 如仍存在），保持权限并记录代码提交与 schema 版本。运行中不能只复制主 `.sqlite3` 文件，应使用 SQLite 在线备份 API。例如由有权读取数据库的操作者执行下列模板，先替换目标路径；不要覆盖已有备份：

```python
from pathlib import Path
import os
import sqlite3

os.umask(0o077)
source = Path('/var/lib/zhbot/bot.sqlite3')
target = Path('/SECURE_BACKUP_DIRECTORY/zhbot-YYYYMMDD.sqlite3')
# 父目录须预先存在且权限受控。独占创建，避免覆盖已有备份。
with target.open('xb'):
    pass
with sqlite3.connect(source.as_uri() + '?mode=ro', uri=True) as db:
    with sqlite3.connect(target) as backup:
        db.backup(backup)
```

恢复前停服务，保留原目录，验证备份完整性与属主/权限，再使用与备份 schema 兼容的代码。本应用 schema 1–4 事务性升级到 5；未知旧快照数据库拒绝打开。不要回退到不支持 schema 5 的旧代码。先在隔离副本核对账本、未完成订单、消息队列和 bot_id，禁止测试副本连接真实 Telegram。

备份恢复可能丢失备份之后的发送/入账记录，数据库无法凭空知道实际已发送内容或外部资金变化。**不得盲目启动旧待发队列或重做积分调整。** 操作者须先对照真实聊天记录、账本和人工依据核实恢复窗口；必要时保持停机。当前没有自动灾备协调、多主机锁或外部对账导入工具。
